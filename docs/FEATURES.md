# Functional Scope

This document summarises the functional modules demonstrated by the ProcureFlow portfolio project.

## 1. Home and navigation

The application uses a persistent navigation structure to give users direct access to their main work areas.

Typical destinations include:

- Home
- Statistics / reporting
- My tickets
- Team tickets
- Create request
- Team management
- Continuous improvement
- Administration / settings

## 2. Request creation

The creation experience adapts to the request type while preserving a common workflow.

Representative request categories include:

- new part / catalogue item;
- quotation request;
- purchase-order request;
- non-catalogue purchase;
- follow-up request;
- other request.

The form supports business validation, optional/mandatory fields depending on context, supporting documents and a final review step.

## 3. Review before submission

Before transmission, the requester can verify the key information in a structured summary.

This reduces avoidable errors and makes the submitted request easier for the receiving team to understand.

## 4. Assignment

A submitted request can be routed to:

- a destination team;
- a named owner.

The receiving owner can then accept responsibility for the ticket.

## 5. My tickets

A personal work queue provides a focused view of requests currently owned or followed by the user.

Useful information can include:

- request number;
- request type;
- requester;
- assigned owner;
- team;
- priority / urgency;
- status;
- creation date;
- latest update.

## 6. Team tickets

The team queue provides visibility over the workload of the service rather than only the current user.

This supports assignment, workload management and operational continuity.

## 7. Request detail

The detail screen acts as the operational workspace for a request.

It can expose:

- request summary;
- current owner;
- status;
- history;
- comments;
- copied stakeholders;
- supporting documents;
- email / conversation context;
- reassignment actions;
- closure controls.

## 8. Documents

Documents created or attached during the request lifecycle remain associated with the request.

The document experience is designed so that the request detail view can expose both original and later-added documents without relying on local temporary storage.

## 9. Comments and history

Comments provide collaboration around the request while history provides traceability of meaningful lifecycle events.

These two concepts are kept distinct so that operational discussion does not replace system traceability.

## 10. Stakeholders / copies

Additional stakeholders can be associated with a request for visibility and selected notifications without automatically becoming owners of the work.

## 11. Email / conversation experience

The application can surface an email-oriented side panel so that a user can understand the communication context around a ticket without making the public portfolio dependent on a real mailbox.

## 12. SharePoint browser / document search

The interface includes a document-navigation pattern designed to help users search or browse SharePoint content from the business application.

The portfolio demonstrates the UX concept while keeping all real tenant URLs private.

## 13. Team management

Administrative screens support concepts such as:

- team creation;
- membership;
- transfers;
- multiple memberships where required;
- access delegation;
- display of team identity.

## 14. Profile and access

The profile area centralises user-oriented settings and access information relevant to the application.

## 15. Closure and archive behaviour

Once a request is closed, the design can restrict further modification and transition the ticket into an archived state according to the business lifecycle.

---

# Portfolio demonstration objective

The demo does not attempt to expose every internal automation or production rule. Its purpose is to make the complete business journey understandable to a recruiter, hiring manager, client or technical reviewer in a few minutes.
